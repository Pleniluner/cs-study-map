## 📋 课程定位与资料地图

软件工程研究的不是“怎样把代码写出来”这一件事，而是怎样让一群人在需求会变化、时间和资源有限的条件下，持续交付正确、可靠、可维护的软件。本目录的材料贯穿软件生命周期：项目与过程、需求工程、UML 分析、架构和面向对象设计、编码规范、单元测试、白盒与黑盒测试、敏捷协作、配置管理以及维护。

## 📚 软件工程核心知识体系

### 软件、工程与职业责任

- 软件不只有程序，还包括数据、配置、测试、构建信息、用户与维护文档。
- 软件工程追求系统化、可度量、成本合宜的开发和演化；质量保证从项目早期开始，而不是等编码结束后补测。
- 需求变更越晚，影响通常越会扩散到架构、代码、测试和文档，因此要建立影响分析和变更控制。
- 软件工程师还承担保密、胜任能力、知识产权、诚实沟通与公共利益等职业责任。
- “项目延期就增加程序员”并非普遍有效：新人学习、沟通路径和协调成本可能让后期项目更慢。

### 生命周期与过程模型

掌握需求、分析/规格、设计、实现、集成、测试、部署、运行维护和退役等活动，并理解这些活动在现代项目中通常会迭代交织。

| 过程模型 | 适用判断 | 必须理解的局限 |
| --- | --- | --- |
| 瀑布 | 需求稳定、阶段审查严格、合规交付物明确 | 反馈较晚，早期错误可能在后期放大 |
| 增量开发 | 可以按价值切分功能，需要尽早交付 | 必须维护跨增量架构与回归测试 |
| 原型开发 | 交互或需求不清，需要低成本试验 | 探索性原型不能未经整理直接变成产品 |
| 螺旋模型 | 技术、成本或安全风险较高 | 风险识别与评估能力决定过程是否有效 |
| RUP | 面向对象、用例驱动、重视架构基线 | 需要按项目规模裁剪，避免流程和文档过重 |
| Scrum/敏捷 | 需求持续变化，可频繁获得用户反馈 | 敏捷不等于无设计、无文档或无计划 |

RUP 的要点是**用例驱动、架构为中心、迭代和增量**；生命周期可理解为初始、细化、构建、过渡。敏捷强调个体协作、可工作的软件、客户合作和响应变化，但每次迭代仍需明确目标、完成定义和可验证增量。

### 项目管理、质量与演化

- 用 W5HH、工作分解结构、责任分配矩阵、任务网络、甘特图和里程碑把目标转为可管理工作。
- 掌握关键路径法：计算最早/最晚开始与完成时间、松弛时间，识别决定最短工期的活动；缩短非关键任务不一定缩短项目。
- 持续管理需求、技术、人员、进度和成本风险，记录概率、影响、应对措施、负责人和触发条件。
- 理解可靠性、健壮性、易用性、可维护性、可移植性、互操作性、性能和安全等质量属性，并把它们写成可检验约束。
- 理解软件质量保证、配置管理、版本基线、变更审批、缺陷跟踪、度量和过程改进；维护包括纠错、适应、完善与预防性修改。

## 🔍 需求分析与 UML 建模

### 需求工程闭环

1. **确定范围与利益相关者**：说明业务目标、系统边界、用户、外部系统和不在范围内的内容。
2. **获取需求**：通过访谈、观察、现有流程、原型和场景发现真实需要，而不只记录用户提出的解决方案。
3. **分析与分类**：区分功能需求、非功能需求、领域规则、接口约束和数据约束，发现冲突、遗漏及异常路径。
4. **规格化**：为需求编号，写明前置条件、触发、主成功场景、备选/失败场景、输入输出和验收标准。
5. **验证**：检查需求是否正确、完整、一致、必要、可行、无歧义、可追踪且可测试。
6. **管理变更**：建立基线，记录来源、优先级、状态和版本；变更前分析对设计、代码、测试、进度的影响。

例如，SATM 的“密码可重试三次”不能只画成一个“登录”椭圆；还要明确失败计数、退出条件、与账户系统的交互以及验收用例。物资管理系统的“归还”也要区分线上申请、线下验收、损坏处理和管理员确认。

### 模型各自回答什么问题

| 模型 | 核心问题 | 常见错误 |
| --- | --- | --- |
| 泳道图/活动图 | 谁在什么顺序下完成业务活动，分支和并发在哪里 | 把界面按钮当业务目标，遗漏失败和回退路径 |
| 数据流图 | 数据从哪里来、经过什么处理、存到哪里、流向何处 | 混入控制流或不逐层平衡输入输出 |
| 用例图与用例描述 | 系统为哪些参与者提供什么目标 | 用例粒度不一致，滥用 `include`/`extend`，没有详细场景 |
| 类图 | 系统有哪些稳定概念、职责、属性、操作和关系 | 从名词机械地产生类，混淆关联、聚合、组合、泛化与实现 |
| 序列图 | 一个场景中对象按时间如何协作 | 消息与类职责不一致，只画理想路径 |
| 状态图 | 一个对象受事件驱动如何转换状态 | 把流程步骤误当对象状态，遗漏守卫条件与异常事件 |

模型必须相互追踪：需求中的关键场景应能在用例描述中找到，在设计模型中有负责对象，在测试集中有对应验收用例。图画得漂亮但不能解释、不能映射到实现和测试，不算完成建模。

### 最小需求交付包

一个练习项目至少应提交：范围说明、利益相关者表、带编号的需求列表、非功能需求、两份详细用例、业务流程图、领域/分析类图、需求—测试追踪表，以及未决问题和变更记录。可使用[2017 项目平台题](hw/2017/需求分析作业-2017秋.pdf)重新完成这一套交付物。

## ⚙️ 架构、设计与实现

### 设计原则

- **抽象与模块化**：每个模块有单一清晰职责，接口表达稳定承诺，实现细节被隐藏。
- **高内聚、低耦合**：把共同变化的内容放在一起，减少对具体类、全局状态和内部数据结构的依赖。
- **关注点分离**：界面、领域逻辑、持久化、外部服务和基础设施不要相互缠绕。
- **为变化设计**：先识别真实可变点，再通过接口、策略、组合和依赖反转隔离变化；不要为了“套模式”增加无意义层次。
- **为复用设计**：优先复用清晰的小组件和组合关系；继承必须表达稳定的可替换关系。
- **简单与可追踪**：设计应足以满足需求和质量属性，每项重要决策都能追溯到具体约束。

架构层面应能识别分层/抽象机、仓库/数据中心、客户端—服务器和事件驱动等风格，并根据数据共享、部署、扩展、可靠性与团队边界说明选择理由。

### 面向对象设计与设计模式

- 从职责与协作识别对象，使用 CRC 思想检查“谁负责什么、需要谁帮助”。
- 正确表达 UML 中的依赖、关联、聚合、组合、泛化和接口实现，并让代码结构与类图保持一致。
- 用序列图检查接口是否足以完成关键场景，用状态图检查有生命周期对象的合法转换。
- 掌握 State、Observer、Factory Method/Abstract Factory、Template Method 等模式解决的变化类型，而不是只记类图。
- [交通灯设计题](hw/2015/homework5/作业5-设计.pdf)要求用 State 模式处理红—黄—绿转换，并讨论左转灯、倒计时灯等变化，适合训练开放扩展与复用边界。

### 实现与评审

- 统一命名、缩进、文件结构和接口约定；让自动检查处理格式问题，把评审精力留给正确性和设计。
- 用清晰代码表达“做什么”，用少量注释解释“为什么”；避免重复代码、魔法数字和与实现不一致的注释。
- 通过前置条件、断言、异常与防御性检查明确非法输入和失败行为，但不能用断言替代必要的运行时错误处理。
- 小步提交，每次提交保持可构建、可测试，并写明意图；代码、模型、测试和文档需要一同演化。
- 评审时检查需求覆盖、职责、依赖、异常路径、资源释放、测试难度与安全边界，而不只检查语法。

## 📊 测试、质量与项目管理实践

### 从规格到结构的测试体系

| 层次或方法 | 学生必须掌握 | 质量证据 |
| --- | --- | --- |
| 静态验证 | 需求/设计评审、代码审查、规范检查、静态分析 | 评审记录、问题清单、检查报告 |
| 单元测试 | xUnit 结构、测试夹具、断言、异常测试、隔离与可重复性 | 自动化测试代码和结果 |
| 白盒测试 | 控制流图、语句/判定/条件覆盖、基本路径、圈复杂度 | 覆盖报告、未覆盖原因、路径用例 |
| 黑盒测试 | 等价类、边界值、判定表、因果关系、状态转换、错误推测 | 由规格推导的测试设计表 |
| 集成测试 | 自顶向下/自底向上、桩与驱动、接口和数据契约 | 集成顺序、接口测试、缺陷记录 |
| 系统与验收 | 功能、性能、可靠性、易用性、安全与用户场景 | 验收标准、环境、数据和报告 |
| 回归测试 | 变更后重跑受影响测试并保留历史基线 | 持续可重复的测试集 |

建议按“失败测试—最小实现—重构”的短循环练习测试驱动开发。一个好测试必须有清楚的意图、可判定的断言、彼此独立的数据和稳定的结果；只执行代码却不检查结果，不构成有效验证。

覆盖率是发现遗漏的线索，不是正确性的证明。语句覆盖不能保证分支，分支覆盖不能穷尽条件组合，路径覆盖在循环和复杂分支中通常无法穷尽。应同时检查测试是否来源于需求、是否包含边界和失败行为、断言是否足够敏感。圈复杂度可用于估计独立路径数量并发现过于复杂的模块，但不能代替设计判断。

可以先阅读[xUnit 示例测试](hw/2015/homework1/test_findobj.py)理解测试结构，再用[文件解压测试](<hw/2015/Homework/作业4 - Coverage/03_white_box/test_fileutil.py>)练习分支和异常，最后对 Splay 树或自己设计的模块同时完成白盒与黑盒测试。

### Scrum 与协作交付

针对[跨馆借阅 Scrum 作业](<hw/2017/软件工程作业 2 - Agile过程.pdf>)，应把一个月拆成若干短 Sprint，而不是简单地把“需求、设计、编码、测试”各安排一周。每个 Sprint 都应包含：

1. 明确的 Sprint Goal 和按价值排序的 Product Backlog。
2. 可在本次迭代完成的用户故事、验收标准与任务拆分。
3. 持续集成、代码审查、测试和可运行增量。
4. Sprint Review 中的真实演示与利益相关者反馈。
5. Retrospective 中对协作、质量和流程的具体改进。

版本控制提交、Issue、评审、测试结果和迭代演示共同构成过程证据。提交次数或代码行数可以辅助观察，但不能单独代表贡献或软件质量。

| 3. 需求工程 | 获取、分类、规格、验证、变更 | 完成[物资管理系统需求题](<hw/2016/软工需求分析作业唐玉涵/97900874_4_作业3 - 需求.pdf>) | 小型 SRS、泳道图、DFD、用例与验收标准 |
| 4. 分析与设计 | 类职责、对象协作、状态、架构与模式 | 连续完成 SATM 的[需求](hw/2015/homework2/作业4-需求.pdf)和[设计](hw/2015/homework5/作业5-设计.pdf) | 类图、序列图、状态图、设计决策记录 |
| 5. 实现质量 | 代码规范、接口契约、断言、评审、Git | 整理一份历史 Python/Java 源码并运行规范检查 | 可读源码、评审记录、清晰提交历史 |
| 6. 单元与白盒 | xUnit、TDD、控制流、覆盖率、复杂度 | 为一个模块补正常、异常和边界测试 | 自动化测试、覆盖报告、未覆盖说明 |
| 7. 黑盒与系统 | 等价类、边界值、判定表、集成、验收 | 独立完成三角形或新业务规格的测试设计 | 测试计划、设计表、缺陷和回归集 |
| 8. 敏捷交付 | Backlog、Sprint、评审、回顾、配置管理 | 重新设计跨馆借阅的迭代计划 | 可运行增量、发布说明、基线和回顾 |
| 9. 综合闭环 | 需求—设计—代码—测试追踪 | 选择一个小系统从零完成并接受同伴评审 | 可复现项目包与追踪矩阵 |

每完成一个阶段，都要回答三个问题：产物服务于谁、如何验证它、发生变更时哪些下游内容必须同步修改。

## ⚠️ 历史资料使用说明

- 本目录主要来自 2013—2017 年，在线评测地址、网页链接、工具安装方式和依赖版本可能已经失效；学习方法和原理，工具则使用当前环境中可维护的等价方案。
- PyUnit 1.4.1、旧式 Python 代码、JUnit/Checkstyle 的历史包、`.class`、`.pyc`、`.jar`、覆盖率数据和压缩包是课程时代样本，不应直接当作现代项目模板或可信可执行文件。
- 历年试卷、同学报告和“参考答案”用于理解题型与比较思路，不保证完整或权威。先独立完成，再检查模型是否一致、测试是否充分。
- UML 图可能保存在图片、Visio 或 PDF 中。阅读图形时要同时核对文字需求，避免因图片缺字、字体或转换问题误解关系。
- 覆盖率高、图数量多、提交次数多都只是局部指标；它们必须与需求满足、断言质量、设计合理性和实际可运行结果结合解释。
- 修改练习时应复制到自己的工作目录，保留这里的历史资料作为只读参照。

## ✅ 结课验收清单

完成学习后，应能在不照抄样卷答案的情况下逐项通过以下检查：

- [ ] 能用自己的话解释软件工程、软件生命周期、质量保证和配置管理的关系。
- [ ] 能针对具体项目比较至少三种过程模型，并说明所选过程如何控制风险与反馈。
- [ ] 能写出编号明确、无明显歧义且可测试的功能/非功能需求和详细用例。
- [ ] 能画出相互一致的用例图、类图、序列图，并为有复杂生命周期的对象补状态图。
- [ ] 能从质量属性推导架构与接口设计，并用高内聚低耦合、信息隐藏和变化隔离解释取舍。
- [ ] 能识别 State、Observer 等模式真正解决的问题，也能说明何时不应使用模式。
- [ ] 能写出命名清楚、行为明确、通过规范检查且便于测试的代码。
- [ ] 能用 xUnit 覆盖正常、边界、异常和状态路径，断言可准确暴露错误。
- [ ] 能解释语句、分支、条件和路径覆盖的区别，并说明覆盖率为何不能证明正确。
- [ ] 能从规格推导等价类、边界值和判定表，并把测试追踪到具体需求。
- [ ] 能编制 WBS、任务依赖、关键路径、里程碑和风险应对，并根据进展更新计划。
- [ ] 能设计包含 Backlog、Sprint Goal、完成定义、评审与回顾的敏捷迭代。
- [ ] 能交付可构建源码、测试数据、自动化结果、设计说明、版本基线、变更记录和已知限制。
- [ ] 能完成一套期末样卷，并用工程原理解释答案，而不只是复述术语。

当这些产物之间能够相互追踪，而且另一位同学能在干净环境中复现、验证并继续维护你的项目时，才算真正掌握了这门课。
